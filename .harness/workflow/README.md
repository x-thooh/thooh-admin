# 流程层：一次修改怎么走完全程

阶段清单在 `flow.json`，**这里是唯一事实源**；本文件讲为什么这么排、怎么跑、失败往回退到哪。
规则（`AGENTS.md`）说「做什么」，断言（`scripts/`）说「有没有做到」，本层说「按什么顺序做、
每一步怎么算过」。

## 怎么跑

五段循环（盘点 → 规划 → 行动 → 反思 → 交付）不是额外负担，它就是把根 `AGENTS.md`
「开工四步」展开成有门径的阶段。每段的过法写在 `flow.json` 的 `gate`（一条 `make` 目标）或
`manual`（明写人判，附理由）里：

| 阶段 | 门径 | 停下来问自己的那句话 |
| --- | --- | --- |
| 盘点 | `make check` | 改之前长什么样，我说得出来吗？ |
| 规划 | 人判 + `contract.md` 六问 | 这批验收规则里，有几条其实没人检查？ |
| 行动 | `make check` | 这一批是不是只改了一类东西？ |
| 反思 | `make selftest` | 这次加的断言真的会报吗？上升归因了吗？ |
| 交付 | `make evidence` | 「修好了」有命令 + 退出码 + 完整输出兜着吗？ |

## 什么时候跑

- 任何一次要改仓库的动作都跑它，包括**给 harness 自己加层**（本批就是例子：建 workflow
  这一层本身走了五段）。
- 小改动也走，只是每段更短：改一行错别字，盘点 = `git status`，交付 = 一次提交。
  段数不许省，只许压缩。
- 回退：反思段发现新欠、或造出的违规样本没打中，**回到行动段**重做，不许带着未归因的上升交付。
  `flow.json` 里 `reflect → act` 那条转移就是这件事的结构化写法。

## 怎么验证装好了

```text
make check        # workflow 段 0 条：flow.json 齐、转移表指向真阶段、声明与磁盘对得上
make selftest     # FLOW001–FLOW010 各有违规样本，外加一条干净树正对照
```

反向验证本层自己的做法：临时把 `flow.json` 里 `deliver` 阶段的 `gate` 改成 `make ghost`，
`make check` 必须报 FLOW004；改回来必须回 0 条。判不了（`workflow/` 整个不在）时报 FLOW001，
与「通过」分得很开。

## 可安装流程

`skills.declared.yaml` 是意图（人手维护，脚本只读），`<仓库根>/skills/` 是磁盘，两者双向对账：
多一个报 FLOW008（加了没人知道、不会被加载），少一个报 FLOW007（声明了却没装机）。
每条流程的 `SKILL.md` 必须答齐三件事——什么时候跑、怎么跑、怎么验证装好了（FLOW009）；
只写「怎么跑」的流程是操作手册，不是可安装流程。

本仓库现在装了一条：`skills/add-module/SKILL.md`（加业务模块，两段修改点最容易漏）。

## 与其他层的关系

引用单向：`AGENTS.md` → 本层 → `specs/` → `scripts/` → 状态目录。本层可以引用
`standards.md` 的对照表与 `contract.md` 的六问，**不许**被 `scripts/` 之外的状态文件反向引用为规则。
断言在 `scripts/scopes/workflow.py`（`scope=workflow`）。
